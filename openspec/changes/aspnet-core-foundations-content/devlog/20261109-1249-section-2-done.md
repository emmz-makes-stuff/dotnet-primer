## Decision: snippet-check settings

Snippets are checked with the plain `dotnet new web` analysis level plus `TreatWarningsAsErrors`, not
the samples' `latest-recommended`, `EnforceCodeStyleInBuild` and `.editorconfig`.
- **Why:** under `latest-recommended`, CA1050 ("declare types in namespaces") fails every
  top-level-statement snippet that declares a record.
- **Fit with the spec and design:** `topic-page-content` says "an ASP.NET Core web project" with
  warnings as errors, and D5 says `dotnet new web`. This matches both.
- **Rejected:** wrapping every snippet's types in a namespace block. It hurts readability, and readers'
  own `dotnet new web` projects don't enforce the rule anyway.

## Scratch tooling, outside the repo

It lives in the session scratchpad, so it's lost when the session ends. Recreate it if needed:
- `snip/` holds `global.json` (copied from the repo), a `Directory.Build.props` with only
  `TreatWarningsAsErrors`, and `Web/` from `dotnet new web`.
- `snip/check.sh <file.cs>` copies the file in as `Program.cs` and builds it. It must run unsandboxed,
  because NuGet and dotnet are blocked in the sandbox.
- `checklinks.mjs <docs-relative .md…>` follows Learn's redirects (locale and `?view=`) and prints OK
  when the final page is a 200 on the same path. Run it through `ctx_execute`, because node `fetch`
  fails DNS in Bash. It needs the 15-second per-request timeout: without one, a run hung for more than
  2 minutes.
