# Probe results (1.1)

<!-- Section: 1 · Task: 1.1 · Base: f03d091 -->

This was a scratch `dotnet new web` API on SDK 10.0.403, with
`Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.14 and `AddAuthentication().AddJwtBearer()`. Its
issuer, audiences and `SigningKeys` came only from `Authentication:Schemes:Bearer` in configuration
(environment variables), with no `Authority`. HS256 tokens were minted by a small node script. The
scratch project is in this session's scratchpad (`sec-probe/`), so treat it as gone after a clear.

## Configuration-only JWT bearer works (D2)

- `SigningKeys` (`Issuer`, base64 `Value`) bind from configuration, and no metadata is fetched
  without an `Authority`. A valid token gets 200.
- **`MapInboundClaims` binds from configuration** (`…:Bearer:MapInboundClaims=false`).
- **`NameClaimType` and `RoleClaimType` do not.** `…:Bearer:TokenValidationParameters:RoleClaimType`
  had no effect. They need code, and a code lambda combines with the configuration section:

  ```csharp
  builder.Services.AddAuthentication().AddJwtBearer(o =>
  {
      o.MapInboundClaims = false;
      o.TokenValidationParameters.NameClaimType = "sub";
      o.TokenValidationParameters.RoleClaimType = "role";
  });
  ```

  With that, `Identity.Name` is `cust-1` and `RequireRole("support")` passes.
- **With mapping on (the default):**
  - `sub` becomes `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifier`;
  - `role` becomes `http://schemas.microsoft.com/ws/2008/06/identity/claims/role`, so `RequireRole`
    works;
  - `Identity.Name` is null for a token with only `sub`.
- **With `MapInboundClaims=false` only:** claim names match the token, but `RequireRole` fails (403),
  because `RoleClaimType` is still the long URI.

So the exercise sets all three in code, in TODO 1 (design D3, revised below).

## Status codes and headers (D5)

| Request | Status | `WWW-Authenticate` |
| --- | --- | --- |
| no token | 401 | `Bearer` |
| expired 1 minute ago | **200** | — (within `ClockSkew`) |
| expired 10 minutes ago | 401 | `Bearer error="invalid_token", error_description="The token expired at '11/11/2026 11:02:33'"` |
| signed with another key | 401 | `Bearer error="invalid_token", error_description="The signature key was not found"` |
| another audience (`aud: someone-else`) | 401 | `Bearer error="invalid_token", error_description="The audience '(null)' is invalid"` |
| another issuer | 401 | `Bearer error="invalid_token", error_description="The issuer 'evil' is invalid"` |
| valid, missing scope | 403 | none |

- `ClockSkew` is the default 5 minutes: 1 minute past expiry passes, and 10 is refused.
- The wrong-audience description really says `'(null)'`, not the token's audience. That's
  IdentityModel hiding PII by default. The page quotes the expired-token header only.

## Scopes (D3)

- **A token with `scope: "orders:read orders:write"`** (one space-separated string, as OAuth
  providers such as Cognito send it) **fails `RequireClaim("scope", "orders:write")`** (403). With
  `scope: "orders:write"` alone, it passes. This confirms the pitfall.
- **`dotnet user-jwts` writes several scopes as a JSON array** (`"scope":["orders:write","orders:read"]`).
  The handler makes one `scope` claim of each, so `RequireClaim` passes for its tokens.
- **So the exercise's helper must handle both:** take every `scope` claim, and split each one on
  spaces. The Starter's "works, but badly" variant (2.4) uses `RequireClaim`, and must fail only the
  space-separated multi-scope test.

## `dotnet user-jwts` (D2)

`dotnet user-jwts create --scope orders:write --scope orders:read --role support`, in a project
with no `UserSecretsId`:
- **adds `<UserSecretsId>` to the `.csproj`;**
- **writes `Authentication:Schemes:Bearer`** into `appsettings.Development.json`:
  - `ValidAudiences` is every URL in `Properties/launchSettings.json` (here
    `http://localhost:5283` and `https://localhost:7037`);
  - `ValidIssuer` is `"dotnet-user-jwts"`;
- **stores the signing key in user secrets** (`…:SigningKeys:0:Value`, `Length`, `Issuer`, `Id`);
- **prints** `New JWT saved with ID '213aa222'.`, `Name: <OS user>`, `Roles: [support]`,
  `Scopes: orders:write, orders:read`, then `Token: <jwt>`.

The token carries:
- `unique_name` and `sub` (both the OS user name, unless `--name` is given);
- `jti`, `scope`, `role`, and `aud` (the array above);
- `iss: "dotnet-user-jwts"`.

It expires in 3 months.

**Gotchas:**
- **Rebuild after the first `user-jwts`.** The `UserSecretsId` is compiled into the assembly. The
  build made before it couldn't read user secrets, so every token got 401 "The signature key was
  not found". After a rebuild, both tokens got 200 on `/me`, `/write` (scope) and `/support` (role).
- **It rewrites `appsettings.Development.json`** unless the file is already in its own format:
  arrays on one line per item, and no final newline. A second run on its own output changed
  nothing. A file with the same values, but a one-line array and a final newline, was rewritten.
  So the exercise ships `appsettings.Development.json` in exactly that format, with a
  `UserSecretsId` and a `launchSettings.json` with fixed ports. Then `user-jwts` changes no tracked
  file (2.5 checks it).

## Rate limiter, antiforgery, HSTS (D11)

- **Rate limiter** (fixed window, 2 per minute, no queue): `200 200 503 503` by default, and
  `200 200 429 429` with `RejectionStatusCode = 429`. `AddFixedWindowLimiter` needs
  `using Microsoft.AspNetCore.RateLimiting;`, because it isn't in the web SDK's implicit usings.
- **Antiforgery** (minimal API, `UseAntiforgery`, a `[FromForm]` parameter):
  - a post without the token gets **400**, `BadHttpRequestException: Invalid anti-forgery token
    found when reading parameter "string name"`;
  - with the token from `GetAndStoreTokens` and its cookie, it gets 200. The field is
    `__RequestVerificationToken`, and the cookie `.AspNetCore.Antiforgery.<suffix>`.
- **HSTS** (`UseHsts` outside Development):

  | Request | `Strict-Transport-Security` |
  | --- | --- |
  | Production, `https://localhost` | none: localhost is in `ExcludedHosts` by default |
  | Production, `http://` | none: only sent over HTTPS |
  | Production, `https://localhost`, `ExcludedHosts` cleared | `max-age=2592000` (30 days, no `includeSubDomains`) |
  | Development, `ExcludedHosts` cleared | none (not called in Development) |

  So the page's HSTS check runs in Production with `ExcludedHosts` cleared, and it says why
  localhost is excluded.
