# 1.2: the exercise's test approach works, with no timing

<!-- Section: 1 · Task: 1.2 · Base: 1f98ddf -->

This was a scratch web app and xUnit v3 test project (`probe11/` in this session's scratchpad,
treat it as gone). It used the samples' own `Directory.Build.props`, `Directory.Packages.props`,
`.editorconfig` and `global.json`, so warnings were errors under the same analyzers. Three runs gave
the same results, apart from the timings.

## The IL check for blocking (design D3): works

`BlockingCalls.In(MethodInfo)` (about 80 lines with comments, no package) reads a handler's IL.
For an `async` handler it reads `AsyncStateMachineAttribute.StateMachineType.MoveNext`. It resolves
each `InlineMethod` operand with `Module.ResolveMethod`. The handler's `MethodInfo` comes from the
`RouteEndpoint`'s metadata (`Metadata.GetMetadata<MethodInfo>()`), found by `RoutePattern.RawText`
in the `EndpointDataSource`.

| Handler | Returns | Found |
| --- | --- | --- |
| sync, `.GetAwaiter().GetResult()` | `IResult` | `TaskAwaiter<T>.GetResult()` |
| `async`, `.Result` inside | `Task<IResult>` | `Task<T>.Result` |
| `async`, `.Wait(token)` inside | `Task<IResult>` | `Task.Wait` |
| `async`, correct | `Task<IResult>` | none |
| `async`, three sequential awaits | `Task<IResult>` | none |
| `async`, `Task.WhenAll` then three awaits | `Task<IResult>` | none |

**The gotcha the design missed:** the compiler's own `await` calls `GetResult()` in `MoveNext`.
So the check counts awaiter `get_IsCompleted` calls, and flags a `GetResult()` only when it comes
with no `IsCompleted` check of its own. The last two rows prove that awaits aren't flagged. It covers
`TaskAwaiter`, `TaskAwaiter<T>` and both `ConfiguredTaskAwaitable` awaiters. `Task.Result`,
`Task<T>.Result` and `Task.Wait` are never emitted by the compiler, so any call to them counts.

**A consequence for the Solution:** after `Task.WhenAll`, read the results with `await stock`, not
`stock.Result`. The check only looks at `POST /orders`, but `.Result` after `WhenAll` is still a bad
example to set.

## Cancellation through `TestServer`: works

A client `PostAsync` with a token. The fake's `ReserveAsync` signals that it started, and the test
cancels then. The client sees `TaskCanceledException`, and the fake's `Task.Delay(Infinite, token)`
throws, so it records the cancellation. `RequestAborted` reaches the handler's `CancellationToken`.

## The barrier for `/quote`: works

A `Barrier(3)`. Each of the fake's three quote calls does `Task.Run(() =>
barrier.SignalAndWait(5 s))`, off the request's thread:
- concurrent (`Task.WhenAll`): 200 in 9 ms;
- sequential: the first call times out after 5 s, and throws a `TimeoutException`, so the response
  is a 500 after 5013 ms.

The test asserts the status, with a TODO 4 hint, not the time.

## The lost failure: works

The fake's `NotifyAsync` returns a faulted task. The test polls `GetFakeLogCollector()` for an Error
for up to 5 s.
- `_ = NotifyAsync(…)`: 202, and no Error log;
- through the channel and a `BackgroundService` that awaits in a `try`/`catch` and logs with a
  `[LoggerMessage]`: 202, then `Notifying the warehouse about order 1 failed.`

## Analyzer findings for the real exercise

- **CA1050:** every type needs a namespace. Put the app's types in `Async.Orders` files, not after
  the top-level statements.
- **CA1711:** a type name ending in `Queue` is refused, so `NotificationQueue` (design D2) becomes
  **`OrderNotifications`**.
- **CA1001:** a fake that owns a `Barrier` must be `IDisposable`, and the factory disposes it in
  `Dispose(bool)`.
