## What ran

- **The SQL Server container:**
  `docker run -d --name efprobe-sql -e ACCEPT_EULA=Y -e 'MSSQL_SA_PASSWORD=Your_strong_password1' -p 14330:1433 mcr.microsoft.com/mssql/server:2025-CU9-ubuntu-24.04`
  - **The pin:** `2025-CU9-ubuntu-24.04` is the newest CU tag on MCR on 2026-11-10.
  - **Image:** amd64, 1.76 GB. It was already in OrbStack's cache, so I didn't time a pull.
  - **Platform:** OrbStack on aarch64 runs it under Rosetta with no settings.
  - **Startup:** "SQL Server is now ready for client connections" appeared 13 s after `docker run`.
- **`dnx -y dotnet-ef@10.0.14 …` works with no install:**
  - `migrations add InitialCreate` created `Migrations/<ts>_InitialCreate.cs`, its `.Designer.cs`
    and `OrdersDbContextModelSnapshot.cs`;
  - `database update` applied it;
  - `migrations script --idempotent` printed `IF OBJECT_ID(N'[__EFMigrationsHistory]') IS NULL …`
    blocks;
  - `migrations bundle --force` built `./efbundle` (about 50 MB), and reminded me to copy
    `appsettings.json` alongside it.

  **The manifest fallback isn't needed.**
- **EF Core 10 takes a migration lock.** `MigrateAsync` and `database update` wrap the run in
  `sp_getapplock @Resource = '__EFMigrationsLock' … 'Exclusive'`, then `sp_releaseapplock`. So the
  page's "don't migrate at startup" reason must **not** claim that concurrent instances corrupt the
  schema. The real reasons are:
  - the app needs DDL rights;
  - startup blocks on the lock;
  - a failed migration takes every instance down;
  - nobody reviews the SQL first.
- **Testcontainers.MsSql 4.16.0 with xUnit v3,** using an assembly fixture,
  `new MsSqlBuilder("<image:tag>").Build()`, and a database per test:
  - **container start:** 10.7 s;
  - **after `MigrateAsync`:** `HasPendingModelChanges()` false, and `GetMigrations().Count()` 1;
  - **model metadata:** `GetMaxLength()` 256, `GetColumnType()` `decimal(10,2)`, precision and
    scale 10,2;
  - **a `DbCommandInterceptor` counting commands that start with `SELECT`:**
    - the projection `Select(o => new { o.Id, LineCount = o.Lines.Count })` gives **1** command
      (`SELECT [o].[Id], (SELECT COUNT(*) FROM [OrderLine] … ) AS [LineCount] FROM [Orders] …`);
    - the loop of `CountAsync` per order gives **6** (1 + 5);
  - **saving 5 orders with their lines in one `SaveChangesAsync`** sent 2 commands: EF batches the
    orders, then the lines. That confirms D4: count `SavedChanges` calls, not SQL batches.
  - **Logging:** `LogTo(…, LogLevel.Information)` shows `Executed DbCommand (…) [Parameters=…]`
    with the SQL. That's the source for the page's SQL listings.
- **No Docker:** a sandboxed run, where the sandbox blocks the Docker socket, fails with
  `DotNet.Testcontainers.Builders.DockerUnavailableException: Docker is either not running or
  misconfigured…`. It names each endpoint it tried (`unix:///var/run/docker.sock` and OrbStack's
  socket).
  - **It's thrown when the fixture is constructed** ("Assembly fixture type 'SqlFixture' threw in
    its constructor"), because `Build()` checks Docker. **So the exercise fixture must build the
    container in `InitializeAsync`**, and catch `DockerUnavailableException` there to rethrow with
    the friendly message.
  - **A bogus `DOCKER_HOST` doesn't simulate a missing Docker:** Testcontainers falls back to
    `/var/run/docker.sock` and the Docker contexts. A sandboxed run is the way to check the message
    in 2.3, with no need to stop OrbStack.

## Found: a vulnerable transitive package (needs Emmz)

`Microsoft.EntityFrameworkCore.SqlServer` 10.0.14 depends on `Microsoft.Data.SqlClient` 6.1.7,
which depends on **`System.Security.Cryptography.Pkcs` 9.0.11**. Restore warns:
- **NU1903 (high):** GHSA-846f-f764-76mx, CVE-2026-84008, .NET denial of service;
- **NU1902 (moderate):** GHSA-2fmv-rv2c-59x7, CVE-2026-70162, .NET denial of service.

Both are fixed in 9.0.21 and in 10.0.13 or later. NuGet's newest is 10.0.14. Testcontainers adds no
other vulnerable package. The samples have `TreatWarningsAsErrors`, so **the samples build would
fail**. The fix needs one more package pin, which goes beyond the three agreed, so it's a question
for Emmz.

## Apple silicon switches (checked 2026-11-10)

- **Rancher Desktop:** Preferences → Virtual Machine → **Emulation**. **VZ** is the default
  ("enabled by default"), and **Enable Rosetta support** is a VZ sub-option that "appears only on
  Apple silicon". Source: <https://docs.rancherdesktop.io/ui/preferences/virtual-machine/emulation/>.
- **Colima:** `colima start --vm-type=vz --vz-rosetta` (README; needs macOS 13 or later).
- **Docker Desktop:** "Use Rosetta for x86_64/amd64 emulation on Apple Silicon" (with the Apple
  Virtualization framework VMM), whose default is **Disabled**. **This corrects design D5**, which
  said it was on by default.
- **OrbStack:** works with no settings (seen here).
- **Azure SQL Edge:** "retired as of September 30, 2025", and "no longer supports the ARM64
  platform" (Learn, previous-versions).
- **Microsoft's support statement** (Learn, the SQL Server Docker quickstart): "SQL Server container
  images are supported only on Linux hosts running on Intel and AMD x86-64 CPUs. Emulation or
  translation environments (for example, Rosetta 2, Prism, or QEMU) aren't tested or supported." The
  page must say this plainly.
