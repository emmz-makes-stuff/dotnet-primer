## 6.1: what the probe showed

The scratch project is `efv/Pool` in this session's scratchpad. It needs no database.
- **`AddDbContextPool`:**
  - the context is scoped, the same instance within a scope, and two open scopes get different
    instances;
  - a disposed scope's context goes back to the pool reset: its change tracker is empty, but **custom
    fields keep their values** (`TenantId` came through to the next request);
  - **the pool is first in, first out.** After two scopes have been returned, the next scope gets
    the *older* one. My first probe, and the first version of the exercise test, wrongly expected
    the instance just returned. The test now runs 20 requests in turn and expects fewer than 20
    distinct instances.
  - Plain `AddDbContext` never reuses an instance.
- **`AddPooledDbContextFactory`:**
  - also registers the context as scoped, **from the same pool** (a context returned by a scope then
    came out of the factory);
  - the factory is a singleton;
  - it can sit next to `AddDbContextPool` (both resolve).
- **A pooled context with an extra constructor service:** it resolves from the root provider. A
  scoped one throws "Cannot resolve scoped service 'RequestInfo' from root provider." when scope
  validation is on (ASP.NET Core turns it on in Development). With validation off, it silently
  gets an instance that isn't the request's.
- **`ConfigureDbContext` interceptors** still apply with a pool. The exercise's tests rely on this.
