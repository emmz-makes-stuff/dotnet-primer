  didn't answer … It may still be starting", plus the setup link. `dotnet publish` has 10 minutes,

- **7.2:** `RunningApp.StartAsync` catches a failed start, disposes the container, and throws:
  "A container of the … image started, but the app in it didn't …", with the app's log, without
  timestamps.
- **7.3:** `ProcessUserAsync` reads `docker info`'s `SecurityOptions`. If it finds `name=rootless` or
  `name=userns`, it returns the container's `Config.User` instead (empty means `root`, and `0:0`
  becomes `0`). Otherwise it uses `docker top` as before. This engine's options are
  `name=seccomp,profile=builtin` and `name=cgroupns`, so the normal path runs here. **I forced the
  fallback in a scratch clone:** the Starter's two `RunsAsANonRootUser` tests failed and the
  Solution's passed, against real images. A real rootless engine isn't measured.
- **7.4:** dropped `DockerfileImage.DisposeAsync`. The base removes the image, and `WithCleanUp(true)`
  stays, as the comment says, in case the test process dies.

## Finding: a crashed .NET app as PID 1 doesn't exit

Checking 7.2 against a Starter whose startup throws (no `Warehouse` section, so `ValidateOnStart`
fails), every test still waited **60 s**, even with Testcontainers' `WaitStrategyMode.Running`. The
reason: after `Unhandled exception.`, the container stayed `running`, exit code 0. The `dotnet`
process was spinning, state `R`, with 0:40 of CPU time in 40 s, and `SIGABRT` wasn't in `SigCgt`.
.NET ends with `abort()`, and the kernel ignores a default-action signal sent to PID 1 from inside
its namespace. With `docker run --init`, the same image exits **134**.

So the wait strategy is now a custom `IWaitUntil`, `UntilListening`. It's ready on "Now listening
on", throws on "Unhandled exception.", and keeps `Running` mode for an app that does exit. The
broken Starter now fails 9/9 in about 2 s each, with the cause and the app's log. The normal
Starter still fails 9/9 with the TODO messages (1 ×2, 2 ×2, 3 ×2, 4 ×3), and none of them is a
start failure.

**Open:** this is also a production fact the page doesn't state. A crashed app's container never
exits, so an orchestrator never restarts it. The fix is `--init` (`docker run --init`, or Compose's
`init: true`), or an orchestrator's health check. Adding it to the page is a scope change, so I've
asked Emmz.
