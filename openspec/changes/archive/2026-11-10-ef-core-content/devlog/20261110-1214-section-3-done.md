### SQL listings: re-captured, and fixed to match the log

D1 says listings are "trimmed only of their parameter declarations", so they're now pasted
verbatim, dedented:
- **Projection:** the exercise uses the `OrderSummary` record, so the subquery has **no**
  `AS [LineCount]` alias (that came from the old probe's anonymous type). Removed.
- **N+1:** the parameter is `@order_Id`, not `@o_Id`. Each `COUNT(*)` is now in the log's
  three-line form.
- **Cancel:** the real UPDATE has `OUTPUT 1`, and both saves are preceded by
  `SET IMPLICIT_TRANSACTIONS OFF; SET NOCOUNT ON;`. Both the cancel and concurrency listings now
  carry them. One sentence was added to explain `OUTPUT 1`.
- **Include:** the column list is on one line, as logged.
- **Unchanged, and matched exactly:** `where`, `ExecuteUpdate`, the concurrency UPDATE (`OUTPUT
  INSERTED.[Version]`, `AND [Version] = @p2`), the translation error (the page abridges it with "…"),
  and the `DbUpdateConcurrencyException` message. The insert is one `INSERT … OUTPUT INSERTED.[Id]`,
  then one `MERGE [OrderLines]`, so "in one batch" holds. `EndsWith("@vip.test")` translates to
  `LIKE N'%@vip.test'`. The logged `[Parameters=[@email='?' (Size = 256)], …]` matches the page.

### Claims checked

- **`AddDbContextFactory` registers the context as `Scoped`:** true, and it's the same instance
  within a scope.
- **"A second operation was started on this context instance before a previous operation
  completed":** exact, from `Task.WhenAll` on one context.
- **The decimal warning:** `SqlServerEventId.DecimalTypeDefaultWarning`, logged under
  `Model.Validation` when the model is first built, not at startup. The pitfall now says "a warning
  in the log when the model is first used".
- **A model change with no migration:** the first wording was wrong. The app throws
  `SqlException: Invalid column name 'Notes'`, and `database update` **throws**
  `PendingModelChangesWarning`: "The model for context 'OrdersDbContext' has pending changes. Add a
  new migration before updating the database." The pitfall is reworded to that.
- **Data annotations** `[MaxLength(256)]` and `[Precision(10, 2)]` compile.
- **`dotnet user-secrets init`, then `set`:** works. ("Set UserSecretsId …", "Successfully saved
  ConnectionStrings:Orders to the secret store.") `dotnet ef` picks the secret up.
- **`migrations add InitialCreate`** writes three files (the migration, Designer, snapshot).
  **Gotcha:** on a never-restored project, `dotnet ef` fails with NETSDK1004 (no
  `project.assets.json`). A learner's `dotnet add package` restores, so the page doesn't mention it.
- **`database update`** prints "Acquiring an exclusive lock for migration application", which
  supports the page's lock sentence.
- **`migrations script --idempotent -o migrate.sql`:** guarded by `IF OBJECT_ID(…) IS NULL` and
  `IF NOT EXISTS` (5 of them).
- **`migrations bundle --force`:** writes `./efbundle` (about 50 MB). `./efbundle --help` lists
  `--connection <CONNECTION>`. `./efbundle --connection "…"` against a new database prints "Done."; a
  second run prints "No migrations were applied. The database is already up to date."
- **Image size and start time:** about 634 MB compressed (the sum of the amd64 layer sizes from
  `docker manifest inspect -v`), 1.76 GB unpacked. Ready after 9 s here, 13 s in the last session.
  The page now says "about 650 MB, which unpacks to 1.8 GB" and "10 to 15 seconds".
- **The cheatsheet's `docker run`** now has `--platform linux/amd64`, to match the page.
- **The cheatsheet's fragments** compile against a model that adds a `Customer` with `Orders`, and
  `Payments` and `Version` on `Order`. They're kept as general cheatsheet examples.
- **The "from the exercise" snippets** (the registration, list projection, save (abridged as
  marked), cancel and `OrderConfiguration`) match `Solution/` byte for byte.
