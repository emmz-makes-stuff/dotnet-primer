# Design

## Context

The repo is greenfield. It holds only `docs/` (DISCOVERY, ADRs, dependencies), `openspec/` and
`.claude/`. The foundational calls are already made and binding:

- ADR-0001: Astro 7 + Starlight for the site;
- ADR-0002: GitHub Pages via Actions, behind Cloudflare DNS;
- ADR-0003: .NET 10 samples with xUnit v3.

See `proposal.md` for the motivation and `specs/` for the required behaviour. Machine facts that shape
the design: Node 24 is installed (Astro 7.4.7 needs ≥22.23), and the default `dotnet` is an 11 RC with
10.0.400 and 10.0.403 SDKs also installed.

## Goals / Non-Goals

**Goals:**

- A skeleton where each later content change only **adds Markdown pages and exercise folders**, with no
  structural work.
- The Microsoft Learn and "Report a problem" conventions are **enforced by the toolchain**, not by
  reviewer memory.
- All eight gate commands work, run non-interactively, and exit non-zero on failure.

**Non-Goals:**

- Real teaching content beyond stubs (later changes).
- A finished visual design. This change sets the theme tokens and typography that the design work
  builds on.
- Diagrams (deferred; the lean is committed SVGs) and external link checking (deferred).
- The Makefile and `make deps`. `/emmz:setup` generates those from the gate commands below.

## Decisions

### D1. Repository layout

```
global.json                  # SDK pin (root, so `dotnet` anywhere in the repo honours it)
.editorconfig  .gitignore
.github/workflows/site.yml   # site gates + Pages deploy
.github/workflows/samples.yml
site/                        # Astro + Starlight project (stack `site`)
  astro.config.mjs  package.json  package-lock.json  tsconfig.json
  .prettierrc.json  .prettierignore  vitest.config.ts
  public/CNAME               # dotnet-primer.emmz.dev
  src/content.config.ts      # docsSchema extended with `learn`
  src/content/docs/…         # pages (see D3)
  src/components/…           # component overrides (D4, D5)
  src/styles/theme.css       # customCss
  tests/dist.test.ts         # site test gate (D7)
samples/                     # .NET solution (stack `samples`)
  Directory.Build.props  Directory.Packages.props
  Primer.slnx  Primer.Solutions.slnx
  exercises/01-configuration/{Starter,Solution,Starter.Tests,Solution.Tests,tests}/
```

Inside each exercise folder, project files carry the exercise topic:
`Configuration.Starter.csproj`, `Configuration.Solution.csproj`, `Configuration.Starter.Tests.csproj`
and `Configuration.Solution.Tests.csproj`. The folder names stay generic. Every future exercise joins
the same `Primer.slnx`, and a bare `Starter.csproj` in every exercise would clash on project and
assembly names. *(As built in §7.)*

The root `global.json` was chosen over `samples/global.json` because `docs/dependencies.md` runs
`dotnet --version` from the root. It only affects `dotnet`, never the Node tooling.

### D2. Site configuration

- `site: 'https://dotnet-primer.emmz.dev'` with no `base`, so the root is `/`.
- Starlight `editLink.baseUrl: 'https://github.com/emmz-makes-stuff/dotnet-primer/edit/main/site/'`.
- `customCss`: the three `@fontsource-variable/*` packages first (D6), then `./src/styles/theme.css`.
- `lastUpdated: true`.
- **Telemetry is off.** The `dev`, `build`, `preview` and `lint` scripts run with
  `ASTRO_TELEMETRY_DISABLED=1`. Astro's telemetry writes to `~/Library/Preferences/astro`, which the
  sandbox denies, so the build crashed. A docs build gate shouldn't phone home anyway. Setting it in
  the npm scripts covers local runs, the Makefile and CI alike. The cost is that the `VAR=x cmd` syntax
  isn't Windows-cmd friendly, which is acceptable here. *(As built in §2.)*
- No UI-framework integrations. Any client behaviour is plain TypeScript in a `<script>` tag.
- Pagefind search and Expressive Code copy buttons come built in, so no extra config is needed beyond
  the default languages. Expressive Code already highlights `csharp`, `sh`, `json`, `xml`,
  `dockerfile` and `yaml`.

### D3. Content structure and learning-path order

The sidebar is an explicit `sidebar` config with ordered groups. It is not autogenerated, because the
order *is* the learning path.

| Group | Pages (slug) |
|---|---|
| *(root)* | `index`: introduction, splash template with a card grid linking every area and standalone section |
| Getting started | `platform/dotnet-10-and-cli` |
| Learning path | `aspnet-core/` (overview) → `aspnet-core/configuration` → `aspnet-core/dependency-injection` → `aspnet-core/middleware` → `observability/logging` → `observability/tracing` → `observability/metrics` → `data/ef-core` → `services/grpc` → `testing/` → `security/` → `performance/async-and-performance` → `deploy/containers` → `deploy/orchestration-and-aws` |
| C# language | `csharp/` |
| Coming from .NET 3.5 | `coming-from-3-5/` |
| Cheatsheets | `cheatsheets/dotnet-cli` |

After Middleware, the order is **provisional**. Discovery leaves it open, and it can change later with a
sidebar edit and no structural work. ".NET 10 and the CLI" sits under *Getting started*, ahead of the
spine, so the cheatsheet has a natural home and the first exercise has setup instructions. Starlight's
built-in previous/next pagination follows the sidebar order. Pagination is turned off on the standalone
and cheatsheet pages through frontmatter (`prev: false` / `next: false`).

Alternative rejected: an autogenerated sidebar with numeric filename prefixes. It couples the URLs to
the order, so a reorder would change URLs.

### D4. Microsoft Learn links: schema-enforced frontmatter

Extend `docsSchema` in `src/content.config.ts` with a required field:

```ts
learn: z.array(z.object({
  title: z.string().min(1),
  url: z.url({ protocol: /^https$/, hostname: /^learn\.microsoft\.com$/ }),
})).min(1)
```

The URL check matches the protocol and the **hostname**, not a string prefix, for two reasons.
`z.string().url()` is deprecated in Zod 4, and `astro check` flags it. A hostname match also rejects
lookalike hosts such as `learn.microsoft.com.evil.io`. *(As built in §3.)*

Starlight's built-in 404 route uses a synthetic entry that bypasses this schema, so the
`MarkdownContent` override treats `learn` as possibly absent there (`?? []`).

Each page declares its Learn links in frontmatter. A replaced `MarkdownContent` component renders the
page body, followed by an **"On Microsoft Learn"** block listing them. A missing or empty `learn` field,
or a non-Learn URL, **fails `astro build`** through content-collection validation. That meets the
"caught" scenario at the first gate. Inline Learn links in the prose are still welcome. The block makes
them consistent.

Alternative rejected: links only in the prose, checked after the build. That's weaker: placement is
inconsistent, and it's caught later.

### D5. "Report a problem" link: replace `EditLink`

Override Starlight's `EditLink` component. It renders the stock "Edit page" link and a **"Report a
problem"** link:

```
https://github.com/emmz-makes-stuff/dotnet-primer/issues/new?title=<enc("Problem on: " + page title)>&body=<enc("Page: " + new URL(Astro.url.pathname, site).href + "\n\nWhat's wrong or missing?\n")>&labels=content
```

The link is computed at build time from `Astro.locals.starlightRoute.entry.data.title` and `Astro.url`,
with no client JS. If the `content` label doesn't exist in the repo, GitHub ignores it silently, so it
is harmless. Starlight's `Footer` renders `EditLink` on every page, including the splash `index`
and 404, so the planned `Footer` fallback was **not needed**. The link carries a `data-report-problem`
attribute, which the site test (D7) uses to find it. *(Verified in §3.)*

Alternative rejected: a GitHub issue form (`.github/ISSUE_TEMPLATE/*.yml`) with a `template=` query
parameter. It's a nice later addition, but it's not needed for the behaviour, and plain `title`/`body`
prefill works without one.

### D6. Theme starting point

`src/styles/theme.css` overrides Starlight's CSS custom properties: `--sl-color-accent-*`,
`--sl-color-gray-*`, `--sl-font`, `--sl-font-mono`, and content width, for both light and dark. Fonts
are self-hosted through `@fontsource-variable/*` packages imported in the CSS, with no Google Fonts
calls. The specific typefaces and palette are picked during apply and recorded in a devlog note. The
distinctive design itself comes in a later change.

### D7. Site test gate (`npm --prefix site test`)

Vitest runs `tests/dist.test.ts` against **`site/dist/`**, so it needs a prior build. If `dist/` is
missing, the test fails with "run `npm --prefix site run build` first", instead of passing vacuously.
It parses every built HTML page with **`node-html-parser`** (a dev dependency) and asserts:

1. **Content pages:** every page except `404.html` and Pagefind assets has
   - ≥1 `a[href^="https://learn.microsoft.com/"]` inside the Learn block, and
   - a "Report a problem" `a` whose `href` starts with the issue URL and whose decoded `body` contains
     the page's full `https://dotnet-primer.emmz.dev/…` URL.
2. **Internal links:** every `a[href]` that is root-relative or points at `dotnet-primer.emmz.dev`
   resolves, ignoring the `#fragment`, to a file in `dist/`: `path/index.html`, `path.html`, or an
   asset. Failures list `source → target`.
3. **Structure:** the `index.html` page links to every area and standalone slug from D3. Search is
   wired: `dist/pagefind/pagefind.js` exists, and the Dependency Injection page's main content carries
   `data-pagefind-body`, so Pagefind indexes it. Pagefind's query API is browser-oriented (WASM plus
   relative fetches), so the end-to-end "search returns DI" scenario is checked by hand in
   `npm --prefix site run preview` and recorded in a devlog note.
4. **CNAME:** `dist/CNAME` exists and contains exactly `dotnet-primer.emmz.dev`.

### D8. Site gates and npm scripts

| Gate | Command | Script |
|---|---|---|
| build | `npm --prefix site run build` | `ASTRO_TELEMETRY_DISABLED=1 astro build` |
| test | `npm --prefix site test` | `vitest run` |
| format | `npm --prefix site run format:check` | `prettier --check .` (plugins: `prettier-plugin-astro`; `.prettierignore`: `dist`, `.astro`, `node_modules`, `package-lock.json`) |
| lint | `npm --prefix site run lint` | `ASTRO_TELEMETRY_DISABLED=1 astro check` (needs `@astrojs/check` + `typescript`) |

Also `format` (`prettier --write .`) for authors. Markdown uses `proseWrap: "preserve"`, so prose diffs
stay readable. Pin `engines.node: ">=22.23"` in `package.json`, and add `site/.nvmrc` with `24`.

### D9. Samples structure and gates

- `global.json`: `{"sdk": {"version": "10.0.400", "rollForward": "latestFeature"}, "test": {"runner": "Microsoft.Testing.Platform"}}`.
  `latestFeature` picks the highest installed 10.0.4xx and never an 11.x.
- `Directory.Build.props`:
  - `TargetFramework=net10.0`
  - `Nullable=enable`, `ImplicitUsings=enable`
  - `TreatWarningsAsErrors=true`, `AnalysisLevel=latest-recommended`
  - `EnforceCodeStyleInBuild=true`
- `Directory.Packages.props`: central package management. `xunit.v3`, and
  `Microsoft.AspNetCore.Mvc.Testing` 10.0.x. Versions are resolved during apply. The runner comes from
  `xunit.v3` on MTP, and `OutputType=Exe` is set for the test projects.
- **Shared tests, compiled twice.** Test source lives in `exercises/01-configuration/tests/*.cs`.
  `Configuration.Starter.Tests.csproj` and `Configuration.Solution.Tests.csproj` (D1 naming) each
  `<Compile Include="../tests/**/*.cs" />`, and
  each references only its own app (`Starter` or `Solution`). Both apps expose `public partial class
  Program` for `WebApplicationFactory<Program>`. This gives engineers a red→green loop on the starter,
  with no duplicate test code.
- `Primer.slnx` = all four projects. `Primer.Solutions.slnx` = `Solution` + `Solution.Tests` only.
- **Exercise 01 (Configuration):** a minimal-API app with a `GreetingOptions` class bound from the
  `Greeting` section of `appsettings.json`, and `GET /greeting` returns the configured message.
  - The starter's binding and endpoint body are `TODO`, so it compiles and returns 501.
  - The tests assert the bound value, and also an override through an environment variable, using
    `WebApplicationFactory.WithWebHostBuilder` with in-memory config.
  - The tests carry clear failure messages, for example: "GET /greeting should return the message from
    configuration section Greeting:Message".

| Gate | Command |
|---|---|
| build | `dotnet build samples/Primer.slnx` |
| test | `dotnet test --solution samples/Primer.Solutions.slnx` |
| format | `dotnet format samples/Primer.slnx --verify-no-changes` |
| lint | none: analyzers + `TreatWarningsAsErrors` make the build the lint |

No exercise uses Testcontainers yet. Docker stays in `docs/dependencies.md` for later exercises.

### D10. GitHub Actions

- **`site.yml`**: triggers on `push` to `main`, `pull_request` to `main`, and `workflow_dispatch`.
  - Job `gates` (`ubuntu-latest`):
    1. checkout;
    2. `actions/setup-node` with `node-version-file: site/.nvmrc` and npm cache;
    3. `npm ci --prefix site`;
    4. build → lint → format:check → test, using the exact gate commands;
    5. `actions/upload-pages-artifact` with `path: site/dist`.
  - Job `deploy` (`needs: gates`, `if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'`):
    `actions/deploy-pages`, using environment `github-pages`.
  - Permissions: `contents: read` at workflow level. `pages: write` and `id-token: write` are scoped to
    the `deploy` job only.
  - `concurrency.group: pages-${{ github.ref }}`, with `cancel-in-progress: false`. Deploys from
    `main` serialise, and PR gate runs don't queue behind them, as they would with a single `pages`
    group. *(As built in §8.)*
  - The Pages artifact is uploaded only on non-PR runs from `main`, the same condition as `deploy`.
- **`samples.yml`**: triggers on `push`/`pull_request` touching `samples/**`, `global.json`,
  `.editorconfig` or the workflow file. `.editorconfig` is included because it drives `dotnet format`
  and the code-style build.
  1. `actions/setup-dotnet` with `global-json-file: global.json`;
  2. the three samples gates.

  It is independent of the site deploy, so a samples failure never blocks content going live.
- Action versions are pinned to the current major tags, resolved during apply.

## Risks / Trade-offs

- **[Starlight is 0.x and may ship breaking changes]** → Mitigation: the lockfile pins versions;
  upgrades are explicit changes.
- **[The `EditLink` override may not render on the splash home page]** → Resolved: it renders there
  (D5). The D7 test guards against a regression.
- **[A required `learn` field adds friction for an author of a page with no relevant Learn page]** →
  Mitigation: every in-scope area has Learn coverage. Changing this needs a spec change, which is a
  deliberate act.
- **[The site test depends on build output]** → Mitigation: it fails loudly when `dist/` is missing. The
  Makefile from `/emmz:setup` orders build before test.
- **[`latestFeature` could pick a future 10.0.5xx band]** → Accepted: still .NET 10. The spec pins
  10.0.4xx today, so revisit the spec wording if a 10.0.5xx band ships.
- **[Cloudflare proxying before the certificate is issued blocks HTTPS]** → Mitigation: the manual setup
  steps say DNS-only first (ADR-0002, `docs/dependencies.md`).

## Migration Plan

This is greenfield, with nothing to migrate. Emmz does the first deploy:

1. Push `main`.
2. Set Pages source to *GitHub Actions*.
3. Set the custom domain `dotnet-primer.emmz.dev`.
4. Add the Cloudflare `CNAME dotnet-primer → emmz-makes-stuff.github.io`, DNS-only.
5. Wait for the certificate, then tick *Enforce HTTPS*.

Rollback means re-running the deploy workflow on an earlier commit, or reverting on `main`.
