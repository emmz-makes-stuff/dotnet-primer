## What it showed

- **Connection string:** the API gets **`ConnectionStrings__Orders`**, named after the database
  resource: `Server=127.0.0.1,<port>;User ID=sa;Password=<generated>;TrustServerCertificate=true;Initial Catalog=Orders`.
  **The Containers page's Compose API ran unchanged** (`GetConnectionString("Orders")`, with
  `EnsureCreated`). Aspire also injects `ORDERS_HOST`, `ORDERS_PORT`, `ORDERS_USERNAME`,
  `ORDERS_DATABASENAME`, `ORDERS_URI` and `ORDERS_JDBCCONNECTIONSTRING`, plus the `OTEL_*`
  variables pointing at the dashboard (`OTEL_EXPORTER_OTLP_ENDPOINT=https://localhost:21184`,
  `OTEL_SERVICE_NAME=api`).
- **The SQL Server image Aspire chose: `mcr.microsoft.com/mssql/server:2022-latest`**, which is
  `amd64` only, so it runs under emulation on Apple silicon (the Compose example pinned
  `2025-CU9-ubuntu-24.04`). Its container is named `sql-<random>`, and it isn't persistent: a new
  one each run, so the data doesn't survive. The password is generated.
- **Service discovery:** the shopfront got `services__api__http__0=http://localhost:5380`. Its
  `HttpClient` with `BaseAddress = new Uri("http://api")`, plus ServiceDefaults'
  `AddServiceDiscovery`, reached the API by name: `POST /buy/SKU-1` gave `201 {"id":1,"sku":"SKU-1"}`,
  and `GET /orders` gave `[{"id":1,"sku":"SKU-1"}]`.
- **ServiceDefaults' health endpoints** (from the `aspire-starter` template's
  `Starter.ServiceDefaults/Extensions.cs`, 13.6.5):
  - `AddDefaultHealthChecks` adds one check, `self`, tagged `live`, that's always healthy;
  - `MapDefaultEndpoints` maps **`/health`** (every check: "ready to accept traffic") and
    **`/alive`** (checks tagged `live`), **only `if (app.Environment.IsDevelopment())`**, with the
    comment that exposing them elsewhere "has security implications" (`https://aka.ms/aspire/healthchecks`);
  - measured: in Development, `/health` and `/alive` give `200 Healthy`. The same build with
    `ASPNETCORE_ENVIRONMENT=Production` gives `404` for both. This supports D3: in production the
    app maps its own live/ready pair;
  - its packages: `Microsoft.Extensions.Http.Resilience` 10.10.0,
    `Microsoft.Extensions.ServiceDiscovery` 10.10.0, and OpenTelemetry 1.17.0.
- The starter's AppHost uses `.WithHttpHealthCheck("/health")` on each project, and the web
  frontend uses `new("https+http://apiservice")` as its base address.

## Gotchas (candidates for the page's Pitfalls or notes)

- **A project needs a launch profile with an endpoint.** The first `aspire run` aborted (exit
  134): `Could not create HTTP health check for resource 'shopfront' as no endpoint was found
  matching one of the specified names: https, http`. Aspire takes a project's endpoints from its
  `Properties/launchSettings.json`, and `dotnet new web` makes one, but a hand-made project
  doesn't. Adding an `http` profile fixed it.
- **A port that's taken fails silently.** With 5180/5181 already held on `[::1]` by another
  process (a Vite dev server), Aspire still reported every resource `Healthy`, but `localhost:5181`
  reached the other process. Aspire's proxy (`dcp`) listens on both `127.0.0.1` and `[::1]` when it
  can. On free ports (5380/5381) everything worked. I didn't touch the other process.
- The scratch API needed the same `System.Security.Cryptography.Pkcs` 10.0.14 pin that the repo
  has, because EF Core's SqlServer 10.0.14 pulls in 9.0.11 (NU1902/NU1903). This isn't new, and
  the repo already handles it.
